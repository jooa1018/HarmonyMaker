## 정책과 호환성

- 016은 encrypted_payload의 NULL을 허용하되 active 행은 반드시 암호문을 갖도록 제약한다. 기존 1–15 SQL·이름·체크섬은 그대로다.
- 삭제 트리거는 구버전 앱의 UPDATE에도 암호문을 비운다. 기존 deleted 행도 016 적용 시 비운다. 구버전 읽기 경로는 lifecycle을 확인한 뒤 복호화하므로 삭제 행의 NULL은 읽기 경로에 진입하지 않는다.
- 새 소유자 삭제는 이미 차단·만료된 행에서도 암호문을 비우며 해당 상태를 유지한다. 차단을 owner-deleted로 바꾸어 새 생성 복구 경로를 허용하지 않는다.
- 만료 공유는 expires_at 후 30일, 차단 공유는 disabled_at 후 30일에 행을 삭제한다.
- 소유자 삭제의 토큰·소유 증거는 원래 expires_at 후 30일까지 유지한다. 암호문은 즉시 지우되 기존 owner reconciliation을 유지하기 위한 tombstone이다.
- 신고·감사는 생성 후 365일이다. 아직 유효한 신고 처리 claim은 종료/만료까지 보존한다. FK SET NULL로 남은 감사·신고를 유지한다.
- 만료 세션은 공유·객체·기존 OMR·멱등·quota lease·신고 참조가 전혀 없을 때만 삭제한다. OMR·객체 원본은 정리 범위에 추가하지 않는다.
- 기간은 `src/server/cleanup/retention.ts` 한 곳에 둔다.

## 정리 처리량

기본 50건 × 최대 100회 = 종류별 최대 5,000건/호출이다. 만료 quota와 멱등 기록을 동시에 각 5,000건 넣어 실제 일회용 PostgreSQL CI에서 한 번의 scheduler 실행으로 제거되는지, 25초 미만인지 시험한다. 사용 가능한 시간이 짧으면 실제 처리량은 더 적다.

25초 공통 기한과 각 SQL의 남은 기한/최대 5초 statement timeout을 적용한다. 응답 기한 이후에는 다음 묶음을 시작하지 않는다. 네트워크·DB의 진행 중 쿼리 종료와 rollback은 응답 종료보다 늦을 수 있다. 완료된 이전 묶음은 커밋되어 남고 실패 중인 묶음은 롤백된다. dryRun은 한 묶음만 읽고 변경하지 않는다.

일일 만료 유입이 종류별 5,000건 이내이고 DB가 충분히 빠르면 하루 한 번으로 따라간다. 예를 들어 종류별 1,000건 backlog는 20회, 5,000건은 100회다. 5,000건/일을 지속적으로 넘는 부하를 따라간다고 주장하지 않는다. 최대 batch 도달과 제거 수를 운영 로그에서 관찰해야 한다. 별도 운영 cron 변경은 하지 않았다.

## 시험 범위

- 메모리: 소유자 삭제 시 NULL, tombstone 보존, 참조 세션 보존, 30일 경계의 행·세션 삭제.
- 스케줄러: 여러 묶음, 100회 상한, 건너뛴 S3 참조로 무한 반복하지 않음, timeout 후 다음 묶음 금지.
- PostgreSQL: 구버전 삭제 SQL의 트리거 효과, 구버전 runtime 확인 허용·구버전 적용기 거부, dryRun, 30일/365일 경계, active·참조 세션 보존, 차단 상태의 소유자 삭제, 각 5,000건 처리.
- 실제 운영 DB·S3 접속과 배포는 하지 않았다.
