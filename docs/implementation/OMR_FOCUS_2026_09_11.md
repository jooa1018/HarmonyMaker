# OMR 실용성·후단 진단 분리 기록 — 2026-09-11

재개 기준은 `3964bc874e84db387839805b17ca609c3433736d`, 작업 브랜치는 `codex/harmonymaker-astra-runtime-closure`, PR은 #13이다. 시작 시 로컬/원격 HEAD가 같고 작업 트리는 깨끗했다. 기존 JPEG, 원시 출력 3개, `.omr`, 원본 대응표, 독립 대조 자료, 465건의 이력과 recovery bundle을 보존했다. 이번 인식 시험에는 교정 이력이나 정답 자료를 공급하지 않았다. 아래 집계는 자동 인식과 교정 후보의 진단을 합산하지 않는다.

## 독립 판정

1. **자동 OMR 실용성: INCOMPLETE.** 입력 해상도·구간 처리 후보를 로컬에서 시험했으나 누락과 문맥 손실이 늘어 기각했다. provider 자동 인식 개선으로 채택한 변경은 없다. 기존 실제 복원은 여전히 465건의 이력, 후보 이벤트 284개 중 신규 삽입 151개(53.2%)에 의존한다.
2. **동일 JPEG 후보 후단: 격리 진단 PASS, 일반 UI Source 확정 차단 유지.** 보존된 후보로 파싱, 편곡 입력, WAG standard, 악보, Web Audio 전곡 재생, IndexedDB 저장/새로고침, 프로젝트·MusicXML 다운로드/내용 검사를 실행했다. 미확정 곡선 연결 미적용, 불완전 가사 유지, 최초 못갖춘마디의 반주 없음이라는 진단 가정이 있다. 정식 Source 승격이나 사용자 UI 전체 성공이 아니다.
3. **원본 완전 복원: INCOMPLETE.** 전체 가사·일반 문자·제목 등의 원본 충실도, 첫 슬래시로 들어오는 곡선의 의미와 연결 대상이 미확정이다. 원본에 없는 tie/slur/pitch를 만들지 않았다.

`src/domain/source/atomization.ts`는 선택한 절의 lyric token, syllabic/extend/emphasis를 입력에 사용한다. `src/grammar/lifecycle.ts`의 `lyricOnset`은 이어지는 harmony를 새로 attack할지 결정한다. 따라서 가사의 누락·배치·강세는 생성 음의 재발음에 영향을 줄 수 있다. 가사 문자열 자체를 음높이로 변환하는 경로는 확인되지 않았지만, 이를 표시 문제만으로 분류할 수 없다.

제목/작곡자 메타데이터와 일반 문자는 이와 다르다. `directionTextEvents`는 section label과 rehearsal mark를 가져오며, 임의의 words 전체를 보존하는 범용 모델은 아니다. 후보의 일반 words 8개는 진단 MusicXML에 남지 않는다. 원시 XML/bundle은 그대로 보존한다. 제목은 후보에 없는 상태로 표시된다. 이번 작업에서 가사 편집기나 새로운 제품 모드는 추가하지 않았다.

반복/tempo는 곡 순서와 시간에 직접 영향을 준다. `flowFromDirection`의 구조화된 반복 지시, parser의 중간 tempo 변경 차단, 초기 tempo 검사는 유지했다. 이 원본에서 확인한 tempo 62 및 표기 순서를 진단에 사용했다. 미확정 진입 곡선이 어떤 연결 효과를 뜻하는지 모르므로 재생 영향이 없다고 결론 내리지 않는다. 진단은 연결 효과를 적용하지 않은 조건에서만 유효하다.

## 후보 후단 실행과 내보내기 내용

격리 테스트가 읽은 것은 기존 bundle의 candidate XML이다. 이력으로 재구성한 XML이 보존된 candidate와 동일함을 먼저 확인하고, 정상 `verifiedStructuralCandidate`가 거부함을 함께 확인했다. 정답 XML을 새로 만들어 가져오지 않았다.

기존 `importMusicXml` → Review commands/`deriveQuickReview` → `createProjectFromQuickReview` → `generateProjectVariant` → materialize/render/export 함수를 호출했다. WAG standard는 complete, 진단 diagnostics는 0이다. 별도 로컬 origin의 페이지에서 기존 `ProductPracticePlayer`와 `IndexedDbProjectStore`를 그대로 실행했다. 제품 Source 전달 경로를 수정하거나 우회하는 제품 버튼은 없다.

## 자동 인식 시험

보존된 정규화 입력에 현재 `prepare_recognition_frame`을 적용한 결과와 과거 엔진 TIFF는 픽셀 단위로 동일했다. 인식용 crop/확대는 재현 가능했고 원본 업로드는 바뀌지 않았다. baseline interline은 13 pixels이다. `.omr`에는 head 객체가 282개 있지만 raw pitched export는 189개이며, head 객체에는 오인식도 있으므로 282개를 정답으로 세지 않는다. 8개 시스템의 beam 객체 수는 3/3/0/3/4/1/1/0이었다. 누락 이벤트와 잘못된 빔·시간축/성부·마디 구조가 재입력 부담의 중심이다.

[Audiveris 스캔 지침](https://audiveris.github.io/audiveris/_pages/guides/advanced/scanning/)의 약 20 pixels interline 권고를 근거로, 엔진 상수를 바꾸지 않는 입력 후보 하나를 시험했다. 기존 MAX_SCALE 2.25와 프레임당 5M pixels 한도를 유지하며 blank scanline에서 두 프레임으로 나눴다. 사용자 JPEG는 로컬에서 한 번, 독립 자체 제작 8마디 6/8 악보도 한 번 새로 인식했다. 외부 OMR 호출은 0건이다. 준비 단계에서 로컬 Pillow TIFF encoder의 ABI 오류가 있었으나 엔진은 실행되지 않았으며, 동일 PNG 픽셀을 기존 컨테이너의 TIFF encoder로 직렬화해 실제 시험을 수행했다.

프레임 원본 bounding box, 역좌표 affine, 순서를 저장했다. 원본 crop 내 픽셀 영역은 빠짐없이 분할되고 겹침은 0이다. 하지만 기존 staff projection 검출기가 8개 중 4개 staff만 반환했고, 선택된 blank 경계가 위 시스템의 가사를 다음 프레임으로 옮겼다. 픽셀 보존이 음악적 문맥 보존을 보장하지 않음을 확인했다.

시험 엔진은 기존 Audiveris 5.10.2이며 jar/launcher config/eng·kor traineddata의 SHA-256이 baseline 로컬 이미지와 동일하다. 기각했던 smallBeams/indentations/observed-beam-pairs 패치를 사용하지 않았다. 0.15 CPU, 512 MiB, heap 192 MiB, 900초 제한을 유지했다. provider 후처리 이전의 native core 출력으로 비교한다.

정렬은 독립 원본의 물리 마디 영역에 제한한 edit-distance 평가이다. 반복된 같은 음의 실제 identity를 모두 검증한 수치가 아니며, 수행한 UI 교정량도 아니다. pitch/duration/onset/voice/tie/kind를 비교하되 구조·박자·조성·코드 교정은 별도다. baseline의 실제 수행량은 465건이며, 이 최소 정렬 비용으로 대체하지 않는다. 새로운 후보도 이벤트 신규 입력만 최소 137개(284개 기준 48.2%)를 요구한다. 일부 일치 증가와 정렬 비용 감소는 전체 누락, 마지막 성부 소실, 문맥 손실을 상쇄하지 못한다.

그 정렬에서 수정으로 분류된 쌍의 불일치 필드는 baseline→후보 순서로 pitch 139→89, duration 151→91, onset 148→91, voice 30→3, tie-start 29→23, tie-stop 35→24, kind 25→13이다. 한 쌍에 여러 오류가 포함되며, 누락/삭제로 분류된 항목은 이 필드 수에 들어가지 않는다. 따라서 이 수의 감소를 음악 보존 개선율로 해석하지 않는다. 동일 tuple 중복도 시각적으로 확인한 중복 기호 수와 구분한다. 원본과 다른 박자/조성 문맥에 걸린 영역은 baseline 29개, 후보 27개이고 후보는 별도로 두 마디를 완전히 잃었다.

새 JPEG core 실행은 컨테이너 생성부터 완료 관측까지 451.7초, peak memory 500,080,640 bytes, OOM 0이었다. 독립 6/8 악보는 115.1초, 480,575,488 bytes, OOM 0이며 8마디/30개의 pitch·duration은 보존했지만 native 코드가 6개여서 2개가 빠졌다. 기존 provider 전체 흐름의 253.8초/8코드 및 사용자 JPEG의 약 658초에는 provider 후처리 등이 포함되므로 core 시간과 직접 비교하여 속도 개선을 주장하지 않는다.

**후보는 기각했다.** 사용자 JPEG의 자동 성공도, 독립 악보의 전체 코드 인식 PASS도 아니다. 실행용 전처리 변경을 제품/provider에 넣지 않았고, 성공처럼 배포하지 않는다. 재조사 없이 반복할 설정 탐색 대신, 다음 인식 개선에는 complete-system+text 문맥 검증과 마지막 시스템 보존을 먼저 충족해야 한다. 이미 누락된 이벤트를 가짜 pitch로 보충하는 방식은 허용하지 않는다.

## 기존 엔진 유지의 평가 범위

Audiveris의 [공식 한계 문서](https://audiveris.github.io/audiveris/_pages/reference/limitations/)와 [handbook](https://audiveris.github.io/audiveris/_pages/handbook/)는 인식 후 수동 검토의 필요성을 명시한다. 현재 5.10.2 Shape 목록에는 일반 notehead 및 percussion 모양은 있지만 rhythm-only slash notehead 전용 형태를 확인하지 못했다. 이 JPEG에서 slash 자동 인식이 되지 않는 결과와 일치하지만, 모든 입력이나 다른 엔진의 불가능성을 의미하지 않는다.

대안은 공식 자료만 별도로 검토했다. [homr](https://github.com/liebharc/homr)는 segmentation+transformer 방식과 CPU 실행을 제공하지만, [vocabulary](https://github.com/liebharc/homr/blob/main/Vocabulary.md)는 박자 분자를 마디 길이에서 재구성한다고 명시한다. 이 입력의 박자 변경과 원본 권한을 고려하면 단순 교체 근거가 아니다. [oemer](https://github.com/BreezeWhite/oemer)도 독립 후보이나 이번 세션에서 새 엔진의 설치·성능 시험이나 채택은 하지 않았다. 512 MiB 적합성, slash·코드·가사 보존, 이 JPEG 정확도에 대한 대안 엔진 PASS는 없다. 독립 평가 가능성을 열어 두되 provider 유지가 인식 품질 최적이라는 결론도 내리지 않는다.
