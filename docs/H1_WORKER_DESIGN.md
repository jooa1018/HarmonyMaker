# [H1] 1-11 긴 곡 측정·Worker 경계 — 부분(A등급 설계 판정 요청)

120마디에서 가장 긴 정지는 생성과 저장·재개 무결성 검사다. 이 계산과 IndexedDB를 Worker 안에서 함께 수행하고, 화면에는 판정 요약·ABC·PlaybackPlan만 돌려주는 방안을 제안한다. 악보 그리기도 CPU 4배 감속에서 수초이므로 Worker 이동만으로 전체 화면 정지가 해결되지는 않는다. 이 PR은 측정·설계 기록이며 런타임 구현은 하지 않는다.

## 측정 조건

- 기준: develop `e31568c`, 2026-10-10. 셋잇단 PR과 독립된 코드다.
- H3 `scripts/ui-flow-check.mjs`와 동일한 자작 `wag11/4-4-1.musicxml`을 120마디로 반복하고, 각 음에 마디·음 순번 SHA-256의 앞 16자를 가사로 넣었다. 알토+테너, 390×844 viewport, CDP CPU 감속 1배/4배다.
- 구간 측정은 브라우저용 minify 번들에서 실제 제품 함수를 계측했다. IndexedDB는 매회 새 로컬 브라우저 context이며 실제 DB·S3·공유 서버에는 접속하지 않았다. 저장 뒤 페이지를 다시 열어 module realm의 검증 캐시가 비어 있는 상태에서 읽었다.
- `exportHarmonyProject`와 `importHarmonyProject` 안의 검증·인코딩을 분리 기록했다. 전체 저장/읽기에서 이 시간을 뺀 값은 IndexedDB를 포함한 잔여 처리 시간이다. 순수 디스크 지연만을 뜻하지 않는다.
- `projectPracticeView` 전체에는 표 안의 하위 호출과 structured clone·기타 처리가 포함된다. 하위 행을 전체 행에 다시 더하지 않는다. 반주 생성 행에는 기존 digest 경로가 포함된다.
- 실제 화면 측정은 H3 절차대로 경로를 먼저 열어 예열하고, 파일 업로드→파트 선택→권리 체크→생성→첫 악보 SVG 표시를 측정한다. 개발 서버는 일회용 memory persistence 설정으로 실행했다.
- 각 조건 한 번의 관측값이다. 실기기 iPhone 수치나 통계적 성능 보장이 아니다. OS·브라우저 부하에 따른 변동이 있으므로, 구현 후 같은 조건에서 여러 번 재측정한다.

## 제안할 Worker 경계

| Worker 내부 | 메인 화면 |
|---|---|
| MusicXML 판정, workspace journal·원본 증거 검증 | 파일 선택, 질문·선택·권리 확인 UI |
| WAG authority 로드, 버전별 검증, 생성, 편집 검증 | 요청 id, 단계 안내, 취소 버튼 |
| 프로젝트 import/export, 기존 IndexedDB store | 제목·조·박자·파트 사유 등 반환 요약 표시 |
| active arrangement, 반주·digest, ABC 직렬화, PlaybackPlan | abcjs SVG, 커서, usePracticePlayer와 AudioContext |
| MusicXML/공유 payload 만들기(요청별 동의 포함) | 다운로드와 기존 공유 네트워크 요청 |

1. 파일 bytes를 Worker로 넘기고 `prepare` 결과로 불투명 preparation handle과 화면용 questions/reasons/notes/summary를 받는다. UI가 복사한 workspace나 “검증됨” 플래그를 생성 권위로 받지 않는다. 질문의 응답·파트·confirmedAt은 handle에 대한 명시적 명령으로 보내고 기존 검증을 거친다.
2. 검증된 프로젝트 객체와 graph-local attestation은 같은 Worker realm에 둔다. 저장은 기존 `IndexedDbProjectStore`를 호출하며, 읽기/외부 파일은 반드시 기존 import·무결성 경로를 거친다. 버전 registry와 바이트 동일성 조건을 바꾸거나 캐시 범위를 넓히지 않는다. Worker가 재시작되면 serialized bytes로 다시 검증한다.
3. UI 반환값은 표시·재생 DTO다. project id, description, ABC, PlaybackPlan, tempo, identity와 요청 id를 포함하고, 저장용 프로젝트 그래프를 왕복 복사하지 않는다. DTO를 다시 저장·검증 권위로 받아들이지 않는다. 표시·재생 복사 비용도 다음 성능 시험에 포함한다.
4. 같은 Worker는 명령을 순서대로 처리한다. 응답은 요청 id와 세대 번호를 함께 확인해 오래된 결과를 버린다. 프로젝트 id는 H3가 쓰는 중복 방지 정책을 그대로 전달한다. 생성 재시도로 라이브러리 항목을 추가 생성하지 않는다.
5. 현재 생성 함수가 동기 CPU 작업이므로 진행률 숫자를 추측하지 않는다. 판정/생성/검증/저장/화면 준비의 실제 단계 전환만 알린다. 생성·검증 중 취소는 Worker 종료 후 재생성으로 처리한다. IndexedDB commit 시작 이후에는 “저장 마무리” 상태로 완료/실패를 확인하고, 취소 성공을 거짓으로 알리지 않는다. commit 전 취소와 commit 후 응답 유실을 나눠 시험한다.
6. Worker 로드 실패·해석 불가능한 응답·미등록 버전은 명확한 오류로 끝낸다. 조용히 무결성 검사를 생략하거나 더 느린 메인 스레드 실행으로 전환하지 않는다. 저장 형식, 공유 버전, WAG 버전·음악 규칙·탐색 범위는 이 변경으로 바꾸지 않는다.

## 악보 그리기

abcjs 그리기는 감속 4배에서 약 7.24초로 별도 병목이다. `oneSvgPerLine`만으로는 동기 그리기 중간에 이벤트 루프에 제어를 돌려준다고 보장할 수 없다. Worker 1차 적용 이후 전체 시간과 이 구간을 다시 측정하고, H3 훅에서 화면 가까운 악보 시스템을 작은 묶음으로 그리는 방안을 함께 검증한다.

분할 표시는 조표·박자·임시표·가사·붙임줄·이음줄·셋잇단과 전역 커서 위치를 보존해야 한다. ABC 텍스트를 마디선 문자로 단순 분리하지 않는다. abcjs의 지원 API로 상태를 보존할 수 있는지 먼저 작은 검증을 하고, 불가능하면 별도 표시 범위 API 설계를 올린다. 전체 PlaybackPlan과 오디오는 표시 분할의 영향을 받지 않는다. 악보 일부를 영구 생략하거나 규칙·음 수를 줄여 시간을 단축하지 않는다.
